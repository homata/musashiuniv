### 【テーマ1】 データの取得・加工: パイプラインの「水源」

データ分析は、分析するための「綺麗に整ったデータ（原油をガソリンにするための精製）」がなければ始まりません。
データ加工は全工程の8割以上の時間を占める、最も泥臭くも価値の高いステップです。

#### (1) 文字コード（Shift-JIS）との死闘

日本の官公庁や自治体が公開するオープンデータの多くは、Windows（Microsoft Excel）で作成されており、文字コードが `Shift-JIS (cp932)` になっています。これをPythonの標準（UTF-8）のまま `pd.read_csv()` で読み込もうとすると、100%の確率で以下のエラーが発生します。
`UnicodeDecodeError: 'utf-8' codec can't decode byte ...`

##### 🚨 対策コードの極意：
```python
import pandas as pd
# 自治体データを読み込む際の鉄則（cp932を指定することで、Excel独自の特殊文字も巻き込んで解決）
df = pd.read_csv("data.csv", encoding="cp932")
```

#### (2) 「縦の連結」と「横の結合」：concat と merge
バラバラな複数のファイルを合体させて1つの大きな表にする方法には、2つのアプローチがあります。
*   連結（`pd.concat`）：形が同じ表を「縦（または横）」に単純に糊付けします。インデックス番号が重複するのを防ぐため、必ず `ignore_index=True` を指定してきれいに通し番号を振り直すのがマナーです。
*   結合（`pd.merge`）：共通の鍵（キー）をベースに、横に拡張します（ExcelのVLOOKUPと同等）。

##### 🚨 内部結合（inner）による「Silent Data Loss（静かなデータ消失）」の恐怖：
`pd.merge(sales_df, product_df, on="商品ID")` のようにオプションを省略すると、デフォルトで `how="inner"`（内部結合） になります。これは、両方の表に共通して存在する商品IDしか残しません。もし売上履歴の中に「新商品（まだマスタに登録されていないID）」が含まれていた場合、その売上データは合致するマスタがないため、警告もなく自動的に消去されてしまいます。
売上履歴などの元データを絶対に減らしたくない場合は、必ず `how="left"`（左結合） を指定しなければなりません。
```python
# データを消さないための左結合（マスタにない部分は NaN になるが、行は維持される）
merged_df = pd.merge(sales_df, product_df, on="商品ID", how="left")
```

#### (3) 複雑な行ごとの計算：apply ✕ lambda
「もし深夜22時以降の注文なら10%割増し、テイクアウトなら軽減税率8%、店内飲食なら10%」といった、if文を含む複雑な1行ごとの計算を行いたい場合、for文を使うと非常に低速になります。そこで、Pandasの `apply()` と `lambda`（名無しの使い捨て関数） を組み合わせます。

##### 🚨 初心者が100%つまずく `axis=1` の指定漏れ：
```python
# ❌ 動かない：axis=1 がないと、Pandasは「列方向（縦）」に処理をしようとしてエラーになる
df["税込み価格"] = df.apply(lambda row: row["価格"] * 1.1 if row["区分"] == "店内" else row["価格"] * 1.08)

# ⭕ 正しい：axis=1 を明記することで、1行（横方向のレコード）ずつ処理してくれる
df["税込み価格"] = df.apply(lambda row: row["価格"] * 1.1 if row["区分"] == "店内" else row["価格"] * 1.08, axis=1)
```

#### (4) 時系列（DateTime型）を支配する
日付は最初はただの「文字列（2026-08-27）」として読み込まれます。これを `pd.to_datetime()` で日付型に変換することで、曜日や月の集計が劇的に楽になります。
```python
# 日付型への変換
df["日付"] = pd.to_datetime(df["日付"])

# 曜日を数値（0=月, 1=火... 6=日）として取り出し、日本語曜日に変換する
weekday_list = ["月", "火", "水", "木", "金", "土", "日"]
df["曜日"] = df["日付"].dt.weekday.apply(lambda x: weekday_list[x])

# 月だけを取り出す
df["月"] = df["日付"].dt.month
```

### 【テーマ2】 データ解析・記述統計: データの「本質」を見極めるレンズ

データが綺麗になったら、次は「記述統計（データの客観的な要約）」によって、データの中に隠れた傾向を見出します。

#### (1) 「平均値」の甘い罠と「中央値」
「我がカフェの平均客単価は3,000円です。だから全員にお金持ち向けのメニューを売りましょう！」という意思決定は、時として壊滅的なミスを招きます。
例えば、客単価1,000円のお客様が9人と、ビル・ゲイツ氏（客単価20,000円）が1人来店した場合、平均値は `(1000*9 + 20000) / 10 = 2,900円` に跳ね上がります。しかし、ゲイツ氏以外のお客様は全員1,000円しか使っていません。

##### 💡 対策：
このような極端なデータ（外れ値）が混ざる可能性がある場合は、データを順番に並べたときの真ん中の値である `中央値（median）` を見るべきです（この場合は1,000円になり、実態を捉えられます）。

#### (2) データのばらつきを測る「標準偏差（Standard Deviation: $\sigma$）」
「平均値が同じ50点」の2つのクラス（A組とB組）があるとします。
*   A組：全員が48点〜52点（ばらつきが小さく、均質）
*   B組：100点満点が半分、0点満点が半分（ばらつきが極めて大きい）

このデータの「ばらつき具合」を数値化したものが標準偏差（`.std()`）です。
標準偏差とは、直感的に言うと「全員のデータが、平均値から平均してどれくらい離れているか（平均距離）」を表します。
*   標準偏差が 小さい ➡ 平均値の近くにデータがギュッと固まっている。
*   標準偏差が 大きい ➡ データが広範囲に散らばっている（平均値があまり信用できない）。

#### (3) クロス集計（crosstab）とピボットテーブル（pivot_table）
2つのカテゴリカルなデータを掛け合わせて、セグメント（客層）ごとの特徴を暴き出すときに使います。
*   `pd.crosstab(行, 列)`：データの「件数（度数）」を数えるのに適しています。
*   `pd.pivot_table(データ, index=row, columns=col, values=val, aggfunc=集計方法)`：売上の「合計（sum）」や「平均（mean）」をセルごとに算出するのに適しています。

```python
# 店舗別×曜日別の売上合計ピボットテーブル
pivot_df = pd.pivot_table(df, index="店舗名", columns="曜日", values="売上金額", aggfunc="sum")
```

#### (4) 相関分析：関係性を数値化する
「客数（X）」と「売上高（Y）」など、2つの数値データの関係性を -1.0 から +1.0 の間の数値で表したものが 相関係数（`.corr()`） です。
*   +1.0 に近い ➡ 正の相関（客数が増えると、売上もきれいに増える）。
*   -1.0 に近い ➡ 負の相関（気温が上がると、ホットコーヒーの売上がきれいに減る）。
*   0.0 に近い ➡ 無相関（降水量とケーキの注文数には、何の関係もない）。

##### ⚠️ データ分析者最大のタブー：相関関係と因果関係の混同
「交番が多い地域ほど、犯罪発生数が多い（強い正の相関 $r = 0.8$）」というデータが出たとします。これを見て「犯罪を減らすために交番をすべて壊そう！」と判断するのは致命的な誤りです。
実際には、「人口が多い地域（第3の要因）」だからこそ、交番も多く、結果として犯罪件数も多くなっているだけです。
「相関がある（データ上、連動している）」からといって、「原因と結果（因果関係）がある」とは限りません。データ分析では常にこの「擬似相関」を疑う冷静な視点が必要です。

### 【テーマ3】 地理空間情報（GIS）分析: データの「場所」を重ね合わせる

現実社会のデータのほとんどには、緯度・経度などの「位置情報」が含まれています。これを可視化・分析するのがGISの役割です。

#### (1) 丸い地球を無理やり平らにする「座標系（CRS）」の不思議
私たちはスマホで「緯度・経度（35.7371, 139.6732）」という数値を扱っています。これは地球を球体として捉えた角度の値（地理座標系：`EPSG:4326`）です。
しかし、この状態で「店舗から500メートル以内の商圏」を作ろうとして、`.buffer(500)` を実行するとどうなるでしょうか？
システムは「半径『500度』の円」を作ろうとしてしまい、地球を何周も包む巨大な円が生成され、画面がバグります。

##### 💡 解決策：
長さを「メートル」単位で正しく計算するためには、丸い地球を特定の地域に最適化して平らに投影した 「投影座標系（日本の平面直角座標系：関東地方は `EPSG:6677`）」 に `.to_crs()` で変換する必要があります。

```python
import geopandas as gpd
# 1. 経緯度(EPSG:4326)でGeoDataFrameを作成
gdf = gpd.GeoDataFrame(df, geometry=gpd.points_from_xy(df["経度"], df["緯度"]), crs="EPSG:4326")

# 2. 空間演算をする前に、メートル単位(EPSG:6677)に変換！
gdf_meter = gdf.to_crs(epsg=6677)

# 3. これで、正しい半径500メートルの商圏バッファ（ポリゴン）が作れる！
gdf_meter["商圏ポリゴン"] = gdf_meter.geometry.buffer(500)
```

#### (2) 空間結合（Spatial Join）：ピンをバケツに自動で投げ入れる
データ分析で「この店舗の緯度経度データ（Point）」が、「東京のどの市区町村ポリゴン（Polygon）」に含まれているかを判定したいとします。何万件もの緯度経度に対してこれを手書きのfor文でループ判定すると、パソコンが何時間もフリーズします。
これを一瞬で（インデックス技術を使ってミリ秒単位で）解決してくれるのが、空間結合（`.sjoin()`） です。

```python
# 点データ(gdf_shops)が、面データ(gdf_districts)のどれに「含まれるか(intersects/within)」を全自動で判定して結合
joined_gdf = gpd.sjoin(gdf_shops, gdf_districts, how="left", predicate="intersects")
# 結果：各店舗の行に、その店が存在する「区名」が瞬時に合体する！
```

#### (3) 動的Webマップ（folium / leafmap）による感動的な可視化
matplotlibで描くグラフは単なる「静止画」です。
`folium` や `leafmap` を使うと、拡大・縮小ができ、ピンをクリックすると吹き出し（Popup）が出る、Google Mapsのような動的マップをPythonだけで一瞬で構築できます。

```python
import folium
# 中心座標と初期ズームを指定してベースマップを作成
m = folium.Map(location=[35.73, 139.67], zoom_start=14)

# ピンを立てる（PopupにはHTMLも記述可能！）
folium.Marker(
    location=[35.7371, 139.6732],
    popup="<b>江古田店</b><br>割引クーポン配布中！",
    icon=folium.Icon(color="red", icon="coffee", prefix="fa")
).add_to(m)
```

### 【テーマ4】 AI・機械学習: 過去から「未来」を先回りする

「今の売上」を可視化するだけでなく、これまでのデータをもとに「明日の売上を予測する（回帰）」、あるいは「似たようなお客様を自動でグループ分けする（分類・クラスタリング）」のが、AI（`scikit-learn`）の役割です。

#### (1) 機械学習の「黄金のルール」：過去問の丸暗記を許すな
用意した100件のデータをすべてAIの学習用（`.fit`）に使って学習させ、同じ100件のデータを予測（`.predict`）させたところ、精度が100%になりました。しかし、このAIモデルを実務に導入して「新しい明日のお客様」を予測させたところ、ひどいエラーになりました。
これが 過学習（オーバーフィッティング） です。
AIが「過去のデータの偶然起きたノイズ」まで完璧なルールとして記憶してしまったために、新しいデータに対して応用が効かなくなってしまったのです。

##### 💡 解決策：
データを必ず、学習用の 「訓練データ（7割〜8割）」 と、AIには一切見せない 「テストデータ（2割〜3割）」 に事前に分割（`train_test_split`）し、テストデータに対する実力テストの点数をAIの本当の通信簿とします。

#### (2) 回帰と分類：予測したいのは「数値」か「カテゴリ」か？
*   回帰（Regression）：明日の売上高や来客数などの「連続する数値」を予測します。
    *   代表格：線形回帰（Linear Regression）（散布図の点々の中心を通る、最もズレの少ない1本の直線を引く）。説明変数が2列以上の場合は重回帰（Multiple Regression）と呼びます。
    *   AIの通信簿（評価）：決定係数 $R^2$（1.0に近づくほど完璧な予測）や、平均絶対誤差 MAE（予測値が平均して何円ズレているか）。
*   分類（Classification）：このお客様は「リピートする（Yes）」か「しない（No）」かなどの「カテゴリ」を予測します。
    *   代表格：決定木（Decision Tree）（「年齢が30歳以上か？」「来店回数が3回以上か？」といったフローチャート式のルールをAIが自動構築する）。
    *   AIの通信簿（評価）：正解率（Accuracy）（100人中、何人の予測が的中したか）、見逃しを防ぐ再現率（Recall）、空振りを減らす適合率（Precision）。

#### (3) 教師なし学習：正解を教えずにAIに自動整理させる「K-means」
「このお客様は優良顧客です」といったラベル（答え）を人間が実データに与えず、AIに顧客の「客単価（X軸）」と「年間来店回数（Y軸）」のデータだけを渡し、「似ている人を自動で3つのグループに分けて」とだけ指示するのが K-meansクラスタリング（教師なし学習） です。
AIは各グループの「中心点（重心：セントロイド）」を数学的に計算し、データ全体を最もきれいに切り分けるクラスターを自動構築します。
※スケールの違い（購入額の1万円と、来店数の1回では桁が違う）を正すため、事前に平均0、標準偏差1にデータを整える `StandardScaler`（標準化） を噛ませることが鉄則です。

### 【テーマ5】 Webアプリとして社会実装: 「すべての合体」とバイブコーディング

どんなに優れたデータ加工、統計解析、GIS、AIモデルを作っても、それがColabの黒い画面とコードの中に埋もれていては、パソコンが使えないカフェの店長やビジネスのクライアントは誰も使えません。
データサイエンスの最後のステップは、「誰でもボタンやスライダーで簡単に操作できるWebアプリ（ダッシュボード）にして、社会に届けること」です。

#### (1) Streamlit：HTML・JavaScript不要の驚異的Webフレームワーク
通常、Webアプリを作るには、HTML, CSS, JavaScript, サーバー構築といった膨大な勉強が必要です。しかし、`Streamlit` を使えば、「今まで書いてきたPythonのデータ分析コードに、`st.sidebar` や `st.slider` を書き足すだけ」で、プロ並みの動的Webダッシュボードが数分で構築されます。

##### 🔄 リアクティブ・プログラミングの仕組み：
Streamlitの最大の魅力は、ユーザーが画面のスライダーを動かした瞬間、「Pythonスクリプトが上から下まで自動で超高速に再実行される（Rerun）」ことです。
1.  スライダーを動かして「客数 150人」にする。
2.  `visitors = st.slider(...)` の変数に即座に `150` が代入される。
3.  その下にある `pred_sales = model.predict([[visitors]])` が150人をベースに再計算される。
4.  折れ線グラフが瞬時に再描画され、画面が勝手に動き出す！

#### (2) バイブコーディング（Vibe Coding）の本質：AI時代の開発マインド
第12回で、私たちは「完璧な設計図となるプロンプト」をChatGPTに投げ、200行を超えるStreamlit✕AIダッシュボードアプリを、わずか15秒で自動生成（Vibe Coding）させました。

「AIがすべてのコードを一瞬で正確に書いてくれるなら、私たちは何のためにこんなプログラミングを勉強したのだろう？」と思うかもしれません。

それこそが、本コースを修了した皆さんの「最大の価値（審美眼）」になります。

*   AIは完璧に見えるコードを出力しますが、時として「全く見当違いな数式のバグ」や「座標系の指定順の間違い（経緯度の順序が逆になり、店舗が宇宙に飛んでいくバグ）」などを平気で埋め込んできます（ハルシネーション）。
*   プログラミングの基礎と、Pandas・GIS・AIの「内部の仕組み・基礎理論」を体得しているあなただけが、AIの書いたコードをレビューし、バグを見破り、「このライブラリを使って、この設計で実装し直して」と、正しい論理でAIを指揮（ディレクション）することができます。

### 練習問題 2: Pandasの結合（merge）とデータ消失

1.  結合方式が標準で「外部結合(outer)」になっており、商品マスタに存在しない商品IDの売上が消去されたから。
2.  結合方式が標準で「内部結合(inner)」になっており、商品マスタに登録されていない商品IDの売上が、合致しないため消去されたから。
3.  売上履歴に「重複」があったため、結合時にPandasが自動的に重複をクレンジング（削除）したから。

<details>
<summary>👉 練習問題 2 の解答を見る</summary>

*   正解: 2
*   解説: `pd.merge()` のデフォルト（標準）の結合方式は `how="inner"`（内部結合） です。これは「両方のデータフレームに共通して存在するキー（商品ID）のみを残す」というお約束です。そのため、売上履歴の中に「まだ商品マスタに登録されていない、お試し新商品のID」などが混ざっていると、合致するものがマスタ側にないため、売上データ自体が丸ごと消去されてしまいます。売上を1行も消したくない場合は、`how="left"`（左結合＝売上履歴をすべて残し、マスタにない部分はNaNにする）を指定する必要があります。

</details>

### 練習問題 5: Streamlitの再実行システム（Rerun）とボタンの罠

しかし、このボタンを押して金額を表示させたあと、サイドバーに配置された「割引クーポン」のチェックボックスにチェックを入れたところ、先ほど画面に表示されていた「合計金額：3,500円」の表示が一瞬で消えてしまいました。

<details>
<summary>👉 練習問題 5 の解答を見る</summary>

*   正解: 「ユーザーが画面を操作するたびに、Streamlitはコードを上から下まで再実行（Rerun）し、その際にボタンのクリック状態は『False（押されていない）』に戻ってしまうから」
*   解説:
    *   Streamlitは「画面に動きがある（チェックボックスを操作するなど）たびに、Pythonコード全体を最初から完全に読み込み直す」というシステム（リアクティブ・フレームワーク）を持っています。

    *   そのため、ボタンが押された中のインデント処理の中に合計金額を出すコードを書いてしまうと、そのあとに別の操作（クーポンのチェックなど）をしてコードが再実行された際、ボタンの状態が False に戻り、計算処理そのものがスキップされてしまうため、表示されていた金額が消滅します。
    *   実務でこれに対処するには、ボタンの中に計算処理を書くのではなく、チェックボックスやスライダーの状態変化そのものをRerunシステムに直接検知させる（ボタンでの判定に頼らない）設計にするのが定石です。

</details>
