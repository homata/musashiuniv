## イントロダクション：仕様・テスト・デバッグとは？

まずは、プログラムを作る時の基本的な流れ、「仕様」「テスト」「デバッグ」という3つの言葉を、カフェの「新しいレジシステム導入」に例えて理解しましょう。

*   **仕様（ルール決め）**: 「コーヒーは450円」「会員なら50円引きにする」といった、プログラムが**どう動くべきか**のルールです。
*   **テスト（確認）**: 実際に「会員の山田さんがコーヒーを頼んだ時、ちゃんと400円になるかな？」と試してみることです。データ分析でも「このデータを入れたら、ちゃんとこのグラフが出るかな？」と確認することが非常に重要です。
*   **デバッグ（バグ退治）**: もしテストをして「あれ？450円のままになっちゃったぞ？」という時、その原因（バグ：虫）を探して修正する作業のことです。

**【バグ退治（デバッグ）のイメージ図】**
```text
  [ 📝 仕様 ] コーヒー450円, 会員50円引
       │
       ▼
  [ 💻 コード ] price = 450 - 50 (←本当は会員かどうかの条件分岐が必要！)
       │
       ▼
  [ 🧪 テスト ] 非会員の佐藤さんでお会計してみる
       │
       ▼
  [ 🐛 バグ発見！ ] 非会員なのに400円になっちゃった！ (論理エラー)
       │
       ▼
  [ 🛠️ デバッグ ] if文を追加してコードを修正する！
```

## エラーの分類とよくあるエラー

エラーには大きく分けて3つの種類があります。これを知っておくだけで、パニックにならずに済みますよ！

### ① 構文エラー (SyntaxError)
Pythonの文法ルールを間違えている時に出ます。「日本語として成り立っていない」状態です。
*   **例**: 「私 コーヒー 飲む は」
*   **原因**: カッコ `()` やクォーテーション `""` の閉じ忘れ、if文の最後のコロン `:` の忘れなど。一番下に出てくる `^` マークの少し前をチェックしましょう。

#### 代表例
コロン（:）の忘れ  
if 文、for 文、def（関数定義）などの末尾にコロンを付け忘れるパターンです。

```
# ❌ 間違い
if age >= 20
    print("成人です")

# ⭕ 正解
if age >= 20:
    print("成人です")
```

括弧や引用符（クォート）の閉じ忘れ  
( に対する ) や、" に対する " が足りない場合に発生します。
```
# ❌ 間違い
print("Hello World"

# ⭕ 正解
print("Hello World")
```

イコール（=）の使い間違い  
比較条件の中で、比較演算子 == を使うべきところに代入演算子 = を使ってしまう例です。
```
# ❌ 間違い
if x = 10:
    print("xは10です")

# ⭕ 正解
if x == 10:
    print("xは10です")
```

予約語（キーワード）を識別子に使ってしまう  
Pythonの構文として意味が決まっている単語（class, def, return, pass など）に変数は命名できません。
```
# ❌ 間違い
class = "1年A組"

# ⭕ 正解
class_name = "1年A組"
```

f-string（フォーマット文字列）内のクォートのバッティング  
f文字列の中で辞書（dict）のキーを指定する際、外側と内側で同じ引用符を使ってしまうとエラーになります。
```
user = {"name": "Alice"}

# ❌ 間違い（外側も内側もダブルクォート）
print(f"Name: {user["name"]}")

# ⭕ 正解（内側をシングルクォートにする）
print(f"Name: {user['name']}")
```

インデント関連のエラー (IndentationError)  
インデント（字下げ）のズレも SyntaxError の派生種である IndentationError として検出されます。
```
# ❌ 間違い
def say_hello():
print("Hello!")  # インデントがない

# ⭕ 正解
def say_hello():
    print("Hello!")
```

全角スペースの混入  
見た目では気づきにくいですが、コード内に「全角スペース」が混ざると構文エラーになります。
```
# ❌ 間違い（ifとxの間に全角スペースが入っている）
if　x == 10:
    print("10です")
```

### ② 例外 / 実行時エラー (Runtime Error)
文法は合っているけれど、実行しようとしたら「物理的に無理だった」時に出ます。
*   **よくあるエラーと対処法**:
    *   `NameError`: 変数名の間違い（例：`coffee` を `cofee` と打ち間違えた）。
    *   `TypeError`: 型の間違い（例：文字と数字を足し算しようとした）。
    *   `IndexError`: リストの範囲外（例：3人しかいないのに「5番目の人を呼んで」と言った）。
    *   `ZeroDivisionError`: ゼロで割り算をしようとした（データ分析で「来店者0人の日の平均」を出そうとするとよく起きます）。

構文エラー（SyntaxError）が「実行前に文法違反で止まる」のに対し、例外 / 実行時エラー（Runtime Error / Exception）は「コードの文法自体は正しいが、プログラムを実行してみたら問題が発生して止まる」エラーです。

#### 代表例
ZeroDivisionError（ゼロ除算）  
数値を 0 で割ろうとしたときに発生します。
```
# ❌ エラーが発生するコード
result = 10 / 0
# ZeroDivisionError: division by zero

# ⭕ 対処法：割る数が0でないか事前にチェックする、または例外処理（try-except）を使う
divisor = 0
if divisor != 0:
    result = 10 / divisor
```

TypeError（型エラー）  
操作や関数の適用が、データ型と適合しない場合に発生します。（例: 文字列と数値を足そうとしたとき）
```
# ❌ エラーが発生するコード
age = 20
message = "年齢: " + age
# TypeError: can only concatenate str (not "int") to str

# ⭕ 対処法：型変換（str(age)）を行うか、f-string を使う
message = f"年齢: {age}"
```

ValueError（値エラー）  
データ型自体は正しいものの、受け取った「値」が適切でない場合に発生します。
```
# ❌ エラーが発生するコード（数字に変換できない文字を int() に渡した）
num = int("hello")
# ValueError: invalid literal for int() with base 10: 'hello'

# ⭕ 対処法：変換前に isdigit() などで検証するか、try-except でパースする
text = "123"
if text.isdigit():
    num = int(text)
```

IndexError（インデックス範囲外エラー）  
リストやタプルなどの要素数を超えるインデックスにアクセスしたときに発生します。  
(スライスの場合は調整されてエラーにならない)
```
# ❌ エラーが発生するコード（要素が3つのリストなのにインデックス5を指定）
numbers = [10, 20, 30]
print(numbers[5])
# IndexError: list index out of range

# ⭕ 対処法：リストの長さを確認するか、安全なアクセスを行う
if len(numbers) > 5:
    print(numbers[5])
```

KeyError（キーエラー）  
辞書（dict）に存在しないキーを指定して値を取得しようとしたときに発生します。
```
# ❌ エラーが発生するコード
user = {"name": "Alice", "age": 25}
print(user["email"])
# KeyError: 'email'

# ⭕ 対処法：.get() メソッドを使う（キーがなければ None を返す）
print(user.get("email"))  # None が返り、エラーにならない
```

AttributeError（属性エラー）  
そのオブジェクト（型）に存在しないメソッドや属性を呼び出そうとしたときに発生します。
```
# ❌ エラーが発生するコード（数値型には upper() メソッドがない）
num = 123
print(num.upper())
# AttributeError: 'int' object has no attribute 'upper'
```

FileNotFoundError（ファイル未検出エラー）  
存在しないファイルを開こうとした（読み込もうとした）ときに発生します。
```
# ❌ エラーが発生するコード
with open("not_exist_file.txt", "r") as f:
    data = f.read()
# FileNotFoundError: [Errno 2] No such file or directory: 'not_exist_file.txt'

# ⭕ 対処法：pathlib や os.path でファイルの存在確認をする
from pathlib import Path

file_path = Path("not_exist_file.txt")
if file_path.exists():
    with open(file_path, "r") as f:
        data = f.read()
```

NameError（名前エラー）  
定義されていない（宣言されていない）変数や関数を呼び出そうとしたときに発生します。
```
# ❌ エラーが発生するコード（タイポや定義忘れ）
print(total_score)
# NameError: name 'total_score' is not defined
```

#### 💡 実行時エラーを防ぐ基本：try - except
実行時エラーが発生する可能性のある処理は、try - except 構文を使うことでプログラムの強制終了を防ぐことができます。  
try - except 構文については第9回で説明します。

```
try:
    # エラーが起きるかもしれない処理
    number = int(input("数字を入力してください: "))
    result = 100 / number
    print(f"計算結果: {result}")

except ValueError:
    print("エラー: 数字以外の文字が入力されました。")

except ZeroDivisionError:
    print("エラー: 0 で割ることはできません。")

except Exception as e:
    print(f"予期せぬエラーが発生しました: {e}")
```


### ③ 論理エラー (バグ)
**これが一番厄介です！** エラー画面は出ず、プログラムは最後まで動くのに「結果が間違っている」状態です。
*   これを直すために、次の「デバッグ技法」を使います。

```
# ① 構文エラーの例（わざとコロンを忘れています。実行してエラーを見てみましょう）
# if True
#     print("コロンがないよ！")

# ② 実行時エラーの例（わざと変数名を間違えています）
shop_name = "ムサシカフェ"
# print(shop_nam)  # NameErrorが出ます
```

**論理エラー（Logical Error / 構造的バグ）**は、文法チェック（`SyntaxError`）も通るし、プログラムを実行しても画面にエラー（`Runtime Error`）が出ずに**最後まで動いてしまう**エラーです。

文法としては完全に正しいため、「プログラムは人間が指示した通りに完璧に動いているが、人間側の指示（ロジック）が間違っている状態」と言えます。
発見するのが一番難しいエラーでもあります。

---

#### 代表例

境界値の指定ミス（`>` と `>=` の間違い）  
指定した条件の「ギリギリの値（境界値）」で意図しない挙動になります。
```python
# ❌ 論理エラー：18歳が「未成年」と判定されてしまう
def is_adult(age):
    return age > 18  # 18歳が含まれていない！

print(is_adult(18))  # 結果: False（本当は True になってほしい）

# ⭕ 修正
def is_adult(age):
    return age >= 18  # 以上（>=）にする
```

インデックスの 1 ズレ（off-by-one エラー）  
プログラミングのインデックスは `0` から始まるため、回数や範囲を勘違いして 1 回分多く（または少なく）処理してしまう現象です。
```python
items = ["りんご", "みかん", "バナナ"]

# ❌ 論理エラー：「バナナ」が処理されない（len(items) は 3 だが range(2) になっている）
for i in range(len(items) - 1):
    print(items[i])  # 「りんご」「みかん」しか出力されない

# ⭕ 修正
for item in items:
    print(item)  # 直接要素を取り出すのが安全
```

演算子の優先順位の勘違い  
足し算・引き算より**掛け算・割り算が優先される**ルールを失念して、カッコを付け忘れるミスです。
```python
# 平均値を計算したい（テストの点数: 80, 90, 70）
score1, score2, score3 = 80, 90, 70

# ❌ 論理エラー：score3 / 3 が先に計算されてしまう（結果: 193.333...）
average = score1 + score2 + score3 / 3

# ⭕ 修正：カッコで括って足し算を先に計算させる（結果: 80.0）
average = (score1 + score2 + score3) / 3
```

ミュータブル（可変）オブジェクトの参照共有  
Pythonのリストや辞書は「参照（データの場所）」を渡す仕組みのため、片方を変更するともう片方も書き換わってしまうミスです。
```python
# ❌ 論理エラー：a を変更したつもりが b まで変わってしまう
a = [1, 2, 3]
b = a  # 参照がコピーされるだけで、同じ実体を見ている

b.append(4)
print(a)  # 結果: [1, 2, 3, 4] （a も書き換わってしまった！）

# ⭕ 修正：.copy() やスライス [:] で別物として複製する
a = [1, 2, 3]
b = a.copy()
b.append(4)
print(a)  # 結果: [1, 2, 3]（a は無事）
```

可変オブジェクトを関数のデフォルト引数にする  
Pythonの超有名・定番の罠です。関数のデフォルト引数に `[]` などのリストを指定すると、**関数の呼び出し間で同じリストが使い回されます**。
```python
# ❌ 論理エラー：呼び出すたびに過去のデータが残ってしまう
def add_item(item, item_list=[]):
    item_list.append(item)
    return item_list

print(add_item("A"))  # 結果: ['A']
print(add_item("B"))  # 結果: ['A', 'B'] （'B' だけのリストになってほしいのに！）

# ⭕ 修正：デフォルト値には None を使い、関数内で初期化する
def add_item(item, item_list=None):
    if item_list is None:
        item_list = []
    item_list.append(item)
    return item_list
```

ループ内の更新忘れ（無限ループ）  
`while` 文などで、ループを抜けるための条件更新を忘れると、永遠に処理が終わらなくなります。（エラーメッセージすら出ずに固まります）
```python
count = 0

# ❌ 論理エラー：count が増えないため永遠に終わらない
while count < 5:
    print("処理中...")
    # count += 1 を忘れいている！

# ⭕ 修正
while count < 5:
    print("処理中...")
    count += 1
```

### 3種のエラーまとめ

| エラーの種類 | 発生するタイミング | 特徴 |
| --- | --- | --- |
| **構文エラー (`SyntaxError`)** | 実行**前** | 文法違反。1行でもあればプログラム自体が起動しない。 |
| **例外 / 実行時エラー (`Runtime Error`)** | 実行**中** | コードは実行できるが、途中で問題が発生してプログラムが**強制終了**する。 |
| **論理エラー (バグ)** | 実行**中〜完了時** | **エラーが出ずに最後まで完走してしまう**が、結果が人間側の期待と異なる。 |

### ベストプラクティス1: `print()` を使って中身をのぞき見する
計算の途中で変数がどうなっているか、こまめに `print()` を差し込んで確認します。

```
# デバッグの具体例：なぜか割引が2回適用されてしまうバグ
price = 1000
is_student = True
is_member = True

# 学割（200円引き）
if is_student:
    price = price - 200
    print("【デバッグ】学割適用後:", price) # ← ここで中身を確認！

# 会員割（100円引き。ただし学割との併用は不可にしたいのに...）
if is_member:
    price = price - 100
    print("【デバッグ】会員割適用後:", price) # ← ここで中身を確認！

print("最終価格:", price) # 700円になってしまう（論理エラー）

# 解決策：2つ目の if を elif に変えれば、併用不可（どちらか一方）になります！
```

## assert文とテスト

「絶対にこうなっているはずだ！」という前提条件を確認するために、**`assert`（アサート：断言する）文**を使います。
もし条件が `False` だった場合、その場で `AssertionError` を出してプログラムを止めてくれます。

```
# assert文の具体例
def calc_discount(price, discount_rate):
    # 割引率は絶対に 0〜1 の間でなければならない！と断言（assert）します。
    # そうでない場合は、カンマの右側のメッセージを出して停止します。
    assert 0 <= discount_rate <= 1, "エラー：割引率がおかしいです！"
    
    return price * (1 - discount_rate)

print("正常な計算:", calc_discount(1000, 0.2)) # 20%引き

# 下の行のコメントを外して実行すると、安全装置（assert）が作動して止まります！
# print("異常な計算:", calc_discount(1000, 1.5)) # 150%引き！？
```

## コーディングスタイルと PEP 8

プログラミングは「動けばいい」というものではありません。データ分析の現場では、他の人（や未来の自分）がコードを読むことが多いため、**「誰が読んでも読みやすい、美しいコード」**を書くことが重要です。

Pythonには **PEP 8（ペップエイト）** という、世界共通の「美しいコードの書き方マニュアル」があります。

Pythonの理念は、「シンプルで読みやすく、美しいコード」を重視することです。
プログラミング言語のPerlには、「There's More Than One Way To Do It.」（やり方は一つじゃない）という格言があります。
Pythonにも格言があり [「PEP 20 – The Zen of Python」](https://peps.python.org/pep-0020/) には、「明示は暗黙に勝る」「シンプルは複雑に勝る」「可読性は重要」などが掲げられており、誰が読んでも理解しやすいコードを書くことが奨励されています。
このような設計思想により、Pythonは初心者にも扱いやすいプログラミング言語とされています。

### PEP 8 の代表的なルール（今日から真似しよう！）

1. **インデントは半角スペース4つ**（Tabは使わない）。
2. **変数名は小文字とアンダースコア（_）で繋ぐ**（例：`coffee_price`。`CoffeePrice` とは書かない）。
3. **演算子の前後には半角スペースを1つ入れる**（例：`a = b + c`。`a=b+c` とは書かない）。
4. **カンマ `,` の後はスペースを1つ入れるが、前には入れない**（例：``）。

### コーディング規約

コーディング規約は主に下記を目的にしています

* 可読性の向上
   * 誰が書いたコードでも、読みやすく理解しやすいようにする
   * チーム開発やオープンソースプロジェクトでの共同作業を円滑にする
* スタイルの統一
   * インデント、変数名、関数名、空白の使い方などのルールを定め、コードの見た目を統一
   * 複数人が同じルールで記述することで、「慣れた見た目」を維持できる
* バグの予防
   * 曖昧な書き方を避けることで、潜在的なバグの原因となる表現を防ぐ
* ツールとの連携
   * 自動フォーマッタ（例：`black`, `autopep8`）や静的解析ツール（例：`flake8`）が PEP8 に準拠しているため、コード品質を機械的に保てる

このように、PEP8は「Pythonコードを書く際の作法」を定めたガイドラインであり、個人でもチームでも、より良いPythonプログラミングの基盤となるものです。

### PEP8 スタイルガイド

Pythonには、PEP8（Python Enhancement Proposal 8）という、公式スタイルガイド（コードの書き方のルール）があります。
PEP8は、「コードの可読性と一貫性を高めること」を目的としたスタイルガイドです。
 
例）カンマの後ろのスペースが異なるコード
```
スタイルガイドに従う
print(1, 2, 3)

スタイルガイドに従ってない
print(1,2,3)
```

PEP 8で定義されているルール スタイルガイドであるPEP 8で定義されているルールは、大きく3つに分類できます。 

* コードのレイアウトに関するルール 
* コメントに関するルール 
* 命名規約に関するルール 

代表的なルールの例
* インデント: スペース4つ
* 行の長さ: 最大79文字まで
* 空白の使い方	`a = b + c`（余計な空白は禁止）

#### 命名規約

一般的な命名の表記方法は次のとおりです。

| 表記方法                     |　説明                                                                           |
|:----------------------------|:--------------------------------------------------------------------------------|
| CamelCase                   | 単語の先頭の文字を大文字にする (CapWords. CapitalizedWords, StudlyCapsとも呼ばれる) |
| lowercase                   | すべての文字を小文字にする |
| lower_case_with_underscores | 単語すべてを小文字にし、それらをアンダースコアでつなげる (snake_caseとも呼ばれる) |
| UPPERCASE                   | すべての文字を大文字にする |
| UPPER_CASE_WITH_UNDERSCORES | 単語すべてを大文字にし、それらをアンダースコアでつなげる |

PEP8での命名規約は下記となります。

| 用途                        |　スタイル                                   | 用例                           |
|:---------------------------|:--------------------------------------------|:-------------------------------|
| パッケージとモジュールの名前 | lowercase                                    | sysytem, datetime              |
| クラスの名前               | CamelCase                                    | TestCase, HTTPRequest           |
| 関数や変数の名前            | lowercase または lower_case_with_underscores |serialize_response, is_connected | 
| 定数                       | UPPERCASE または UPPER_CASE_WITH_UNDERSCORE  | MAX_OVERFLOW, TOTAL             |
| 例外の名前                  | CamelCase, 末尾にError                       | ClientApiError                 |


PEP8の命名規約で重視されているのは「実装よりも使い方を表した名前」にすることです。
命名に迷ったときは、標準ライブラリや公開されているサードパーティライブラリの命名を参考にしてみるのもよいです。

### 変数名の付け方
* 引用元：[変数名の付け方をまとめてみた](https://zenn.dev/naoki_oshiumi/articles/aad7e1b3719fad)

#### 良い変数名とは
良い変数名は「必要な情報が含まれている」となります。
例えば「name」という変数名はフルネームなのか名字なのか名前なのかが分かりませんが、
「fullName」だと「フルネームなんだな」と理解できます。「name」だと情報不足なことがあります。

良い変数名をつけると「無駄なコメントが減る」「他の開発者にとって読みやすい」などのメリットがあります。
無駄なコメントは開発者を混乱させますし読みにくいコードはバグが生まれる原因になるので、変数名はかなり重要です。

----

#### 変数名をつけるコツ

##### ①広く意味を持つ名前をつけない
先程例に上げた「name」は広い意味を持ってしまっているのでフルネーム？名字？名前？とわからなくなってしまいます。    
他にも「tmp」や「temp」は「一時的」という意味がありますが、意味が広すぎて一時的な何者なのか？が全くわかりません。  
前後の文脈がないと判断できないもの、前後の文脈があっても判断できないものは修正する余地があるでしょう。  

##### ②多少長くなっても必要な情報は必ずいれる
変数名が長いと嫌われる傾向にありますが、個人的には多少長くなっても構わないと思います。    
それより必要な情報を変数名に入れるほうが優先だと思います。

例えば、平文のパスワードの場合「password」ではなく「plain_password」が良いですし、
税込み金額は「price」ではなく「priceIncludingTax」とかの方が良いと思います。
また、税込金額を文字列フォーマットした場合は「formattedPriceIncludingTax」とかの方が良いかもしれません。（もっと適切な英語があるかも）

##### ③不要な単語は排除する
逆に無駄な情報は変数名にはいれないという考え方です。必要な情報を入れた上でなるべく変数名を短くしようということです。  
変数名を無理に短くしようとするあまり必要な情報が削られてしまうと意味がないので、意味がわかる範囲で作成します．  

例えば「convertToString」は「toString」で良いです。  

##### ④日本語をローマ字にした変数名は避ける

```text
「性別」の変数名は「seibetsu」ではなく「gender」
「情報」の変数名は「jyoho」ではなく「information」が良いです。
```

##### ⑤配列やコレクションは複数形にする
例えば「userList」は「users」でOKです。複数系だとuserが複数いるんだとわかります。  

「data」とか「information」のように複数形かどうかわからない場合は「data_array」とかで良いです。

##### ⑥boolean型は「is」「has」「can」「should」をつけると分かりやすくなることが多い

```text
is ... 状態を表す（isActiveとか）  
has ... 所有を表す（hasFileとか）  
can ... 可能を表す（canGetとか）  
should ... すべきかどうか（shouldChangeとか）  
```

isやhasはよく使われます

##### ⑦品詞を意識する
変数名は基本的に「名詞」なので、「名詞のみ」もしくは「形容詞 + 名詞」でつけます。  
たまに変数名なのに動詞になっていることがあるので、品詞を意識してみると良いです。

変数名に限らず、例えば関数名は何かを処理する動作を表しているはずなので基本的に「動詞のみ」もしくは「動詞 + 名詞」のように動詞から始まります。
