第7回 テスト・デバッグ、コードスタイル¶

さて、プログラミングをしていて、赤い文字で「エラー（Error）」が出た時、ドキッとしませんか？「何か壊してしまったかも…」「自分には向いてないのかも…」と不安になる方もいると思います。

今回は、エラーを怖がらずに「バグ（虫）を見つけて退治する技術（デバッグ）」と、エラーを未然に防ぐための「美しいコードの書き方（コードスタイル）」を学びます。 これができるようになれば、今後のデータ分析が驚くほどスムーズになりますよ。一緒に楽しく学んでいきましょう！

🎯 到達目標¶

  1. エラーの種類（構文エラー・実行時エラー・論理エラー）を区別し、適切な対処法がわかる。

  2. print文や生成AIを活用したデバッグ（バグ退治） の具体的なテクニックを使える。

  3. assert文 を使って、プログラムが正しく動いているか「テスト」できる。

  4. PEP 8（ペップエイト） というルールを知り、誰が読んでも読みやすい美しいコードが書ける。

イントロダクション：仕様・テスト・デバッグとは？¶

まずは、プログラムを作る時の基本的な流れ、「仕様」「テスト」「デバッグ」という3つの言葉を、カフェの「新しいレジシステム導入」に例えて理解しましょう。

  • 仕様（ルール決め）: 「コーヒーは450円」「会員なら50円引きにする」といった、プログラムがどう動くべきかのルールです。

  • テスト（確認）: 実際に「会員の山田さんがコーヒーを頼んだ時、ちゃんと400円になるかな？」と試してみることです。データ分析でも「このデータを入れたら、ちゃんとこのグラフが出るかな？」と確認することが非常に重要です。

  • デバッグ（バグ退治）: もしテストをして「あれ？450円のままになっちゃったぞ？」という時、その原因（バグ：虫）を探して修正する作業のことです。

【バグ退治（デバッグ）のイメージ図】

  [ 📝 仕様 ] コーヒー450円, 会員50円引
       │
       ▼
  [ 💻 コード ] price = 450 - 50 (←本当は会員かどうかの条件分岐が必要！)
       │
       ▼
  [ 🧪 テスト ] 非会員の佐藤さんでお会計してみる
       │
       ▼
  [ 🐛 バグ発見！ ] 非会員なのに400円になっちゃった！ (論理エラー)
       │
       ▼
  [ 🛠️ デバッグ ] if文を追加してコードを修正する！

エラーの分類とよくあるエラー¶

エラーには大きく分けて3つの種類があります。これを知っておくだけで、パニックにならずに済みますよ！

① 構文エラー (SyntaxError)¶

Pythonの文法ルールを間違えている時に出ます。「日本語として成り立っていない」状態です。

  • 例: 「私 コーヒー 飲む は」

  • 原因: カッコ () やクォーテーション "" の閉じ忘れ、if文の最後のコロン : の忘れなど。一番下に出てくる ^ マークの少し前をチェックしましょう。

② 例外 / 実行時エラー (Runtime Error)¶

文法は合っているけれど、実行しようとしたら「物理的に無理だった」時に出ます。

  • 例: 「メニューにないタピオカミルクティーを出して！」

  • よくあるエラーと対処法:

    • NameError: 変数名の間違い（例：coffee を cofee と打ち間違えた）。

    • TypeError: 型の間違い（例：文字と数字を足し算しようとした）。

    • IndexError: リストの範囲外（例：3人しかいないのに「5番目の人を呼んで」と言った）。

    • ZeroDivisionError: ゼロで割り算をしようとした（データ分析で「来店者0人の日の平均」を出そうとするとよく起きます）。

③ 論理エラー (バグ)¶

これが一番厄介です！ エラー画面は出ず、プログラムは最後まで動くのに「結果が間違っている」状態です。

  • 例: 「お会計がマイナス500円になった」

  • これを直すために、次の「デバッグ技法」を使います。

# ① 構文エラーの例（わざとコロンを忘れています。実行してエラーを見てみましょう）
# if True
#     print("コロンがないよ！")

# ② 実行時エラーの例（わざと変数名を間違えています）
shop_name = "ムサシカフェ"
# print(shop_nam)  # NameErrorが出ます

デバッグ技法とベストプラクティス（具体例）¶

論理エラー（結果がおかしい！）が起きた時、プロはどうやって原因を探すのでしょうか？

ベストプラクティス1: print() を使って中身をのぞき見する¶

計算の途中で変数がどうなっているか、こまめに print() を差し込んで確認します。

# デバッグの具体例：なぜか割引が2回適用されてしまうバグ
price = 1000
is_student = True
is_member = True

# 学割（200円引き）
if is_student:
    price = price - 200
    print("【デバッグ】学割適用後:", price) # ← ここで中身を確認！

# 会員割（100円引き。ただし学割との併用は不可にしたいのに...）
if is_member:
    price = price - 100
    print("【デバッグ】会員割適用後:", price) # ← ここで中身を確認！

print("最終価格:", price) # 700円になってしまう（論理エラー）

# 解決策：2つ目の if を elif に変えれば、併用不可（どちらか一方）になります！

ベストプラクティス2: 生成AI（ChatGPTなど）を頼る！¶

今の時代、一人で何時間も悩む必要はありません。エラーが出たら、エラーメッセージ全体と自分のコードをコピーして、生成AIに「このエラーの原因と直し方を教えて」と聞いてみましょう。 非常にわかりやすく解説してくれます。これも立派なプログラミングスキルの一つです！

assert文とテスト¶

「絶対にこうなっているはずだ！」という前提条件を確認するために、assert（アサート：断言する）文を使います。 もし条件が False だった場合、その場で AssertionError を出してプログラムを止めてくれます。被害が大きくなる前にストップする安全装置ですね。

# assert文の具体例
def calc_discount(price, discount_rate):
    # 割引率は絶対に 0〜1 の間でなければならない！と断言（assert）します。
    # そうでない場合は、カンマの右側のメッセージを出して停止します。
    assert 0 <= discount_rate <= 1, "エラー：割引率がおかしいです！"
    
    return price * (1 - discount_rate)

print("正常な計算:", calc_discount(1000, 0.2)) # 20%引き

# 下の行のコメントを外して実行すると、安全装置（assert）が作動して止まります！
# print("異常な計算:", calc_discount(1000, 1.5)) # 150%引き！？

pytest（パイテスト）について¶

プロの世界では、こういったテストを全自動で何百個も行ってくれる pytest という強力な外部パッケージ（ツール）を使います。この授業では「そういう便利な自動テストツールがあるんだな」と知っておくだけで今は大丈夫です！

コーディングスタイルと PEP 8¶

プログラミングは「動けばいい」というものではありません。データ分析の現場では、他の人（や未来の自分）がコードを読むことが多いため、**「誰が読んでも読みやすい、美しいコード」**を書くことが重要です。

Pythonには PEP 8（ペップエイト） という、世界共通の「美しいコードの書き方マニュアル」があります。

Pythonの理念は、「シンプルで読みやすく、美しいコード」を重視することです。 プログラミング言語のPerlには、「There's More Than One Way To Do It.」（やり方は一つじゃない）という格言があります。 Pythonにも格言があり 「PEP 20 – The Zen of Python」 には、「明示は暗黙に勝る」「シンプルは複雑に勝る」「可読性は重要」などが掲げられており、誰が読んでも理解しやすいコードを書くことが奨励されています。 このような設計思想により、Pythonは初心者にも扱いやすいプログラミング言語とされています。

PEP 8 の代表的なルール（今日から真似しよう！）¶

  1. インデントは半角スペース4つ（Tabは使わない）。

  2. 変数名は小文字とアンダースコア（_）で繋ぐ（例：coffee_price。CoffeePrice とは書かない）。

  3. 演算子の前後には半角スペースを1つ入れる（例：a = b + c。a=b+c とは書かない）。

  4. カンマ , の後はスペースを1つ入れるが、前には入れない（例：``）。

  5. わかりやすい変数名をつける（例：単なる a や x ではなく、sales_total のように意味を持たせる）。

# 悪いスタイルの例（動くけれど、PEP 8 に違反していて読みにくい！）
a=100
b=200
def calc(x,y):
    return x+y
mylist=

# 良いスタイルの例（PEP 8 に準拠していて美しい！）
coffee_price = 100
cake_price = 200

def calculate_total(price1, price2):
    return price1 + price2

my_list =

コーディング規約¶

主に下記があります。

可読性の向上

  • 誰が書いたコードでも、読みやすく理解しやすいようにする

  • チーム開発やオープンソースプロジェクトでの共同作業を円滑にする

スタイルの統一

  • インデント、変数名、関数名、空白の使い方などのルールを定め、コードの見た目を統一

  • 複数人が同じルールで記述することで、「慣れた見た目」を維持できる

バグの予防

  • 曖昧な書き方を避けることで、潜在的なバグの原因となる表現を防ぐ

ツールとの連携

  • 自動フォーマッタ（例：black, autopep8）や静的解析ツール（例：flake8）が PEP8 に準拠しているため、コード品質を機械的に保てる

このように、PEP8は「Pythonコードを書く際の作法」を定めたガイドラインであり、個人でもチームでも、より良いPythonプログラミングの基盤となるものです。

※ PEP（Python Enhancement Proposal）： Pythonの新機能や改善案を提案・記録するための公式文書です。

種類

内容

技術的PEP

新機能の追加、文法や標準ライブラリの変更など

情報提供PEP

スタイルガイドやプロセス文書（例：PEP8）

プロセスPEP

開発プロセスや意思決定の方法に関する提案

PEP8 スタイルガイド¶

Pythonには、PEP8（Python Enhancement Proposal 8）という、公式スタイルガイド（コードの書き方のルール）があります。 PEP8は、「コードの可読性と一貫性を高めること」を目的としたスタイルガイドです。

例）カンマの後ろのスペースが異なるコード

スタイルガイドに従う
print(1, 2, 3)

スタイルガイドに従ってない
print(1,2,3)

PEP 8で定義されているルール スタイルガイドであるPEP 8で定義されているルールは、大きく3つに分類できます。

  • コードのレイアウトに関するルール

  • コメントに関するルール

  • 命名規約に関するルール

代表的なルールの例

  • インデント: スペース4つ

  • 行の長さ: 最大79文字まで

  • 空白の使い方 a = b + c（余計な空白は禁止）

変数名の付け方¶

  • 引用元：変数名の付け方をまとめてみた

良い変数名とは¶

良い変数名は「必要な情報が含まれている」となります。 例えば「name」という変数名はフルネームなのか名字なのか名前なのかが分かりませんが、 「fullName」だと「フルネームなんだな」と理解できます。「name」だと情報不足なことがあります。

良い変数名をつけると「無駄なコメントが減る」「他の開発者にとって読みやすい」などのメリットがあります。 無駄なコメントは開発者を混乱させますし読みにくいコードはバグが生まれる原因になるので、変数名はかなり重要です。

変数名をつけるコツ¶

①広く意味を持つ名前をつけない¶

先程例に上げた「name」は広い意味を持ってしまっているのでフルネーム？名字？名前？とわからなくなってしまいます。
他にも「tmp」や「temp」は「一時的」という意味がありますが、意味が広すぎて一時的な何者なのか？が全くわかりません。 前後の文脈がないと判断できないもの、前後の文脈があっても判断できないものは修正する余地があるでしょう。

②多少長くなっても必要な情報は必ずいれる¶

変数名が長いと嫌われる傾向にありますが、個人的には多少長くなっても構わないと思います。
それより必要な情報を変数名に入れるほうが優先だと思います。

例えば、平文のパスワードの場合「password」ではなく「plain_password」が良いですし、 税込み金額は「price」ではなく「priceIncludingTax」とかの方が良いと思います。 また、税込金額を文字列フォーマットした場合は「formattedPriceIncludingTax」とかの方が良いかもしれません。（もっと適切な英語があるかも）

③不要な単語は排除する¶

逆に無駄な情報は変数名にはいれないという考え方です。必要な情報を入れた上でなるべく変数名を短くしようということです。

変数名を無理に短くしようとするあまり必要な情報が削られてしまうと意味がないので、意味がわかる範囲で作成します．

例えば「convertToString」は「toString」で良いです。

④日本語をローマ字にした変数名は避ける¶

「性別」の変数名は「seibetsu」ではなく「gender」 「情報」の変数名は「jyoho」ではなく「information」が良いです。

⑤配列やコレクションは複数形にする¶

例えば「userList」は「users」でOKです。複数系だとuserが複数いるんだとわかります。

「data」とか「information」のように複数形かどうかわからない場合は「data_array」とかで良いです。

⑥boolean型は「is」「has」「can」「should」をつけると分かりやすくなることが多い¶

is ... 状態を表す（isActiveとか）
has ... 所有を表す（hasFileとか）
can ... 可能を表す（canGetとか）
should ... すべきかどうか（shouldChangeとか）

isやhasはよく使われます

⑦品詞を意識する¶

変数名は基本的に「名詞」なので、「名詞のみ」もしくは「形容詞 + 名詞」でつけます。
たまに変数名なのに動詞になっていることがあるので、品詞を意識してみると良いです。

変数名に限らず、例えば関数名は何かを処理する動作を表しているはずなので基本的に「動詞のみ」もしくは「動詞 + 名詞」のように動詞から始まります。

📚 第7回のまとめ¶

エラーを恐れずに向き合う「デバッグ」の力と、プロのように美しい「コードスタイル」でした。 これらはプログラミングにおいて、文法と同じくらい大切な部分です。

✨ 今日の重要ポイントまとめ¶

  • エラーの分類: 文法ミス（SyntaxError）、実行時の無理難題（例外）、計算間違い（論理エラー）の3つがある。

  • デバッグ: 論理エラーが出たら、怪しいところに print() を入れて変数の中身を覗き見する。生成AIもどんどん活用する！

  • assert文: 「絶対にこうなるはず！」という前提条件をプログラムに埋め込み、テストの自動化やバグの早期発見に役立てる。

  • PEP 8: 変数名（小文字と_）や、演算子の前後の空白など、みんなが読みやすい「美しいコード」のルール。

❓ よくある質問と回答 (FAQ)¶

  • Q. 生成AIにコードを直してもらったら、自分が書いていない難しい書き方になって返ってきました…。

    • A. AIあるあるですね！そういう時はAIに「プログラミング初心者です。if文など、なるべく簡単な文法だけで書き直して、理由も教えてください」と追加でお願い（プロンプトを工夫）してみましょう。

  • Q. PEP 8のルールを全て覚えないとダメですか？

    • A. 全て暗記する必要は全くありません！まずは「演算子の前後にスペースを入れる」「わかりやすい変数名にする」という基本の2つを意識するだけで、コードは劇的に綺麗になりますよ。

🌟 Colabで試すおすすめコード¶

assert文を使った簡単な「データ品質チェック」のプログラムです。 データ分析では、読み込んだデータが正しい範囲にあるかチェックすることが重要です。

# カフェの顧客の年齢データリスト
age_data = # おや...？200歳の人が混ざっています

# データを一つずつ取り出してチェックします（次回詳しくやる for文を使います）
for age in age_data:
    # 年齢は 0歳以上、120歳以下のはずだと断言します！
    assert 0 <= age <= 120, "あり得ない年齢データが混ざっています: " + str(age)
    print("正常なデータ:", age)
