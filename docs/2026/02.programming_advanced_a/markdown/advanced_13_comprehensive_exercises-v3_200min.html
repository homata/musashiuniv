1. 【テーマ1】 データの取得・高度な加工（第2回〜第3回）: パイプラインの「水源」¶

データ分析は、分析するための「綺麗に整ったデータ（原油をガソリンにするための精製）」がなければ始まりません。データ加工は全工程の8割以上の時間を占める、最も泥臭くも価値の高いステップです。

(1) 文字コード（Shift-JIS）との死闘¶

日本の官公庁や自治体が公開するオープンデータの多くは、Windows（Microsoft Excel）で作成されており、文字コードが Shift-JIS (cp932) になっています。これをPythonの標準（UTF-8）のまま pd.read_csv() で読み込もうとすると、100%の確率で以下のエラーが発生します。 UnicodeDecodeError: 'utf-8' codec can't decode byte ...

🚨 対策コードの極意：¶
import pandas as pd
# 自治体データを読み込む際の鉄則（cp932を指定することで、Excel独自の特殊文字も巻き込んで解決）
df = pd.read_csv("data.csv", encoding="cp932")

(2) 「縦の連結」と「横の結合」：concat と merge¶

バラバラな複数のファイルを合体させて1つの大きな表にする方法には、2つのアプローチがあります。

  • 連結（pd.concat）：形が同じ表を「縦（または横）」に単純に糊付けします。インデックス番号が重複するのを防ぐため、必ず ignore_index=True を指定してきれいに通し番号を振り直すのがマナーです。

  • 結合（pd.merge）：共通の鍵（キー）をベースに、横に拡張します（ExcelのVLOOKUPと同等）。

🚨 内部結合（inner）による「Silent Data Loss（静かなデータ消失）」の恐怖：¶

pd.merge(sales_df, product_df, on="商品ID") のようにオプションを省略すると、デフォルトで how="inner"（内部結合） になります。これは、両方の表に共通して存在する商品IDしか残しません。もし売上履歴の中に「新商品（まだマスタに登録されていないID）」が含まれていた場合、その売上データは合致するマスタがないため、警告もなく自動的に消去されてしまいます。 売上履歴などの元データを絶対に減らしたくない場合は、必ず how="left"（左結合） を指定しなければなりません。

# データを消さないための左結合（マスタにない部分は NaN になるが、行は維持される）
merged_df = pd.merge(sales_df, product_df, on="商品ID", how="left")

(3) 複雑な行ごとの計算：apply ✕ lambda¶

「もし深夜22時以降の注文なら10%割増し、テイクアウトなら軽減税率8%、店内飲食なら10%」といった、if文を含む複雑な1行ごとの計算を行いたい場合、for文を使うと非常に低速になります。そこで、Pandasの apply() と lambda（名無しの使い捨て関数） を組み合わせます。

🚨 初心者が100%つまずく axis=1 の指定漏れ：¶
# ❌ 動かない：axis=1 がないと、Pandasは「列方向（縦）」に処理をしようとしてエラーになる
df["税込み価格"] = df.apply(lambda row: row["価格"] * 1.1 if row["区分"] == "店内" else row["価格"] * 1.08)

# ⭕ 正しい：axis=1 を明記することで、1行（横方向のレコード）ずつ処理してくれる
df["税込み価格"] = df.apply(lambda row: row["価格"] * 1.1 if row["区分"] == "店内" else row["価格"] * 1.08, axis=1)

(4) 時系列（DateTime型）を支配する¶

日付は最初はただの「文字列（2026-08-27）」として読み込まれます。これを pd.to_datetime() で日付型に変換することで、曜日や月の集計が劇的に楽になります。

# 日付型への変換
df["日付"] = pd.to_datetime(df["日付"])

# 曜日を数値（0=月, 1=火... 6=日）として取り出し、日本語曜日に変換する
weekday_list = ["月", "火", "水", "木", "金", "土", "日"]
df["曜日"] = df["日付"].dt.weekday.apply(lambda x: weekday_list[x])

# 月だけを取り出す
df["月"] = df["日付"].dt.month

2. 【テーマ2】 データ解析・記述統計（第4回）: データの「本質」を見極めるレンズ¶

データが綺麗になったら、次は「記述統計（データの客観的な要約）」によって、データの中に隠れた傾向を見出します。

(1) 「平均値」の甘い罠と「中央値」¶

「我がカフェの平均客単価は3,000円です。だから全員にお金持ち向けのメニューを売りましょう！」という意思決定は、時として壊滅的なミスを招きます。 例えば、客単価1,000円のお客様が9人と、ビル・ゲイツ氏（客単価20,000円）が1人来店した場合、平均値は (1000*9 + 20000) / 10 = 2,900円 に跳ね上がります。しかし、ゲイツ氏以外のお客様は全員1,000円しか使っていません。

💡 対策：¶

このような極端なデータ（外れ値）が混ざる可能性がある場合は、データを順番に並べたときの真ん中の値である 中央値（median） を見るべきです（この場合は1,000円になり、実態を捉えられます）。

(2) データのばらつきを測る「標準偏差（Standard Deviation: \(\sigma\)）」¶

「平均値が同じ50点」の2つのクラス（A組とB組）があるとします。

  • A組：全員が48点〜52点（ばらつきが小さく、均質）

  • B組：100点満点が半分、0点満点が半分（ばらつきが極めて大きい）

このデータの「ばらつき具合」を数値化したものが**標準偏差（.std()）です。 標準偏差とは、直感的に言うと「全員のデータが、平均値から平均してどれくらい離れているか（平均距離）」**を表します。

  • 標準偏差が 小さい ➡ 平均値の近くにデータがギュッと固まっている。

  • 標準偏差が 大きい ➡ データが広範囲に散らばっている（平均値があまり信用できない）。

(3) クロス集計（crosstab）とピボットテーブル（pivot_table）¶

2つのカテゴリカルなデータを掛け合わせて、セグメント（客層）ごとの特徴を暴き出すときに使います。

  • pd.crosstab(行, 列)：データの「件数（度数）」を数えるのに適しています。

  • pd.pivot_table(データ, index=row, columns=col, values=val, aggfunc=集計方法)：売上の「合計（sum）」や「平均（mean）」をセルごとに算出するのに適しています。

# 店舗別×曜日別の売上合計ピボットテーブル
pivot_df = pd.pivot_table(df, index="店舗名", columns="曜日", values="売上金額", aggfunc="sum")

(4) 相関分析：関係性を数値化する¶

「客数（X）」と「売上高（Y）」など、2つの数値データの関係性を -1.0 から +1.0 の間の数値で表したものが 相関係数（.corr()） です。

  • +1.0 に近い ➡ 正の相関（客数が増えると、売上もきれいに増える）。

  • -1.0 に近い ➡ 負の相関（気温が上がると、ホットコーヒーの売上がきれいに減る）。

  • 0.0 に近い ➡ 無相関（降水量とケーキの注文数には、何の関係もない）。

⚠️ データ分析者最大のタブー：相関関係と因果関係の混同¶

「交番が多い地域ほど、犯罪発生数が多い（強い正の相関 \(r = 0.8\)）」というデータが出たとします。これを見て「犯罪を減らすために交番をすべて壊そう！」と判断するのは致命的な誤りです。 実際には、**「人口が多い地域（第3の要因）」**だからこそ、交番も多く、結果として犯罪件数も多くなっているだけです。 「相関がある（データ上、連動している）」からといって、「原因と結果（因果関係）がある」とは限りません。データ分析では常にこの「擬似相関」を疑う冷静な視点が必要です。

3. 【テーマ3】 地理空間情報（GIS）分析（第7回〜第9回）: データの「場所」を重ね合わせる¶

現実社会のデータのほとんどには、緯度・経度などの「位置情報」が含まれています。これを可視化・分析するのがGISの役割です。

(1) 丸い地球を無理やり平らにする「座標系（CRS）」の不思議¶

私たちはスマホで「緯度・経度（35.7371, 139.6732）」という数値を扱っています。これは地球を球体として捉えた角度の値（地理座標系：EPSG:4326）です。 しかし、この状態で「店舗から500メートル以内の商圏」を作ろうとして、.buffer(500) を実行するとどうなるでしょうか？ システムは「半径『500度』の円」を作ろうとしてしまい、地球を何周も包む巨大な円が生成され、画面がバグります。

💡 解決策：¶

# 3. これで、正しい半径500メートルの商圏バッファ（ポリゴン）が作れる！

4. 【テーマ4】 AI・機械学習（第10回〜第11回）: 過去から「未来」を先回りする¶

「今の売上」を可視化するだけでなく、これまでのデータをもとに「明日の売上を予測する（回帰）」、あるいは「似たようなお客様を自動でグループ分けする（分類・クラスタリング）」のが、AI（scikit-learn）の役割です。

(1) 機械学習の「黄金のルール」：過去問の丸暗記を許すな¶

用意した100件のデータをすべてAIの学習用（.fit）に使って学習させ、同じ100件のデータを予測（.predict）させたところ、精度が100%になりました。しかし、このAIモデルを実務に導入して「新しい明日のお客様」を予測させたところ、ひどいエラーになりました。 これが 過学習（オーバーフィッティング） です。 AIが「過去のデータの偶然起きたノイズ」まで完璧なルールとして記憶してしまったために、新しいデータに対して応用が効かなくなってしまったのです。

💡 解決策：¶

データを必ず、学習用の 「訓練データ（7割〜8割）」 と、AIには一切見せない 「テストデータ（2割〜3割）」 に事前に分割（train_test_split）し、テストデータに対する実力テストの点数をAIの本当の通信簿とします。

(2) 回帰と分類：予測したいのは「数値」か「カテゴリ」か？¶

  • 回帰（Regression）：明日の売上高や来客数などの「連続する数値」を予測します。

    • 代表格：線形回帰（Linear Regression）（散布図の点々の中心を通る、最もズレの少ない1本の直線を引く）。説明変数が2列以上の場合は**重回帰（Multiple Regression）**と呼びます。

    • AIの通信簿（評価）：決定係数 \(R^2\)（1.0に近づくほど完璧な予測）や、平均絶対誤差 MAE（予測値が平均して何円ズレているか）。

  • 分類（Classification）：このお客様は「リピートする（Yes）」か「しない（No）」かなどの「カテゴリ」を予測します。

    • 代表格：決定木（Decision Tree）（「年齢が30歳以上か？」「来店回数が3回以上か？」といったフローチャート式のルールをAIが自動構築する）。

    • AIの通信簿（評価）：正解率（Accuracy）（100人中、何人の予測が的中したか）、見逃しを防ぐ再現率（Recall）、空振りを減らす適合率（Precision）。

(3) 教師なし学習：正解を教えずにAIに自動整理させる「K-means」¶

「このお客様は優良顧客です」といったラベル（答え）を人間が実データに与えず、AIに顧客の「客単価（X軸）」と「年間来店回数（Y軸）」のデータだけを渡し、「似ている人を自動で3つのグループに分けて」とだけ指示するのが K-meansクラスタリング（教師なし学習） です。 AIは各グループの「中心点（重心：セントロイド）」を数学的に計算し、データ全体を最もきれいに切り分けるクラスターを自動構築します。 ※スケールの違い（購入額の1万円と、来店数の1回では桁が違う）を正すため、事前に平均0、標準偏差1にデータを整える StandardScaler（標準化） を噛ませることが鉄則です。

練習問題 1: データの尺度と統計指標¶

「コーヒー(100円), 紅茶(120円), ジュース(150円)」という商品別の「価格」は ( A ) 尺度であり、その代表値として平均値を計算することに意味があります。一方、「1:非常に満足, 2:満足, 3:普通, 4:不満」というアンケートの評価値は ( B ) 尺度であり、代表値としては「中央値」や「最頻値」が適しています。 空欄(A)と(B)に入る尺度の名称の組み合わせを答えてください。

👉 練習問題 1 の解答と解説を見る

  • 正解: ( A ) = 比例（比率）尺度、( B ) = 順序尺度

  • 解説:

    • 価格は、0円が「無（お金が存在しない）」を意味し、100円の2倍は200円という「掛け算・割り算（比率）」に意味があるため比例尺度です。平均値を計算できます。

    • 満足度アンケートは、1から4の数字に「順序（大小関係）」はありますが、「満足(2)と満足(1)の差が、不満(4)と普通(3)の差と全く等しい」とは言えず、割り算もできないため順序尺度です。アンケート結果を単純に「平均2.3」と出すのは厳密には不適切で、中央値（真ん中の人）や最頻値（最も多い回答）で見るのが基本です。

練習問題 2: Pandasの結合（merge）とデータ消失¶

Pandasで売上履歴データフレーム df_sales（1万行）と、商品マスタデータフレーム df_products（50件）を、共通の「商品ID」を使って pd.merge() で結合しようとしています。 しかし、結合オプションを何も指定せずにマージしたところ、売上履歴が8000行に減ってしまいました。この原因として最も適切なものはどれでしょうか？

  1. 結合方式が標準で「外部結合(outer)」になっており、商品マスタに存在しない商品IDの売上が消去されたから。

  2. 結合方式が標準で「内部結合(inner)」になっており、商品マスタに登録されていない商品IDの売上が、合致しないため消去されたから。

  3. 売上履歴に「重複」があったため、結合時にPandasが自動的に重複をクレンジング（削除）したから。

👉 練習問題 2 の解答と解説を見る

  • 正解: 2

  • 解説: pd.merge() のデフォルト（標準）の結合方式は how="inner"（内部結合） です。これは「両方のデータフレームに共通して存在するキー（商品ID）のみを残す」というお約束です。そのため、売上履歴の中に「まだ商品マスタに登録されていない、お試し新商品のID」などが混ざっていると、合致するものがマスタ側にないため、売上データ自体が丸ごと消去されてしまいます。売上を1行も消したくない場合は、**how="left"（左結合＝売上履歴をすべて残し、マスタにない部分はNaNにする）**を指定する必要があります。

  1. エラーが発生して、プログラムがその場で強制終了する。

練習問題 4: 機械学習の「過学習（Overfitting）」とホールドアウト¶

機械学習において、用意したデータすべてをAIの学習用（.fit）に使ってモデルを構築し、同じデータを使ってモデルの精度（決定係数など）を測定したところ、100%（完璧）の精度が出ました。 しかし、このAIモデルを実務に導入して「新しくやってきた明日のお客様の売上」を予測させたところ、全く当たらないひどい予測になってしまいました。この現象を何と呼ぶでしょうか？また、これを防ぐための機械学習の黄金のルールは何でしょうか？

👉 練習問題 4 の解答と解説を見る

  • 正解:

    • 現象名：過学習（オーバーフィッティング）

    • 黄金のルール：学習データ（訓練データ）と、テストデータ（評価データ）の分割（ホールドアウト法）

  • 解説:

    • 過去のデータを丸暗記（過学習）したAIは、過去の「たまたま起きたノイズ（その日だけ天気が大荒れだったなど）」まで完璧なルールとして記憶してしまいます。そのため、まだ見ぬ未来（未知のデータ）に対する予測力が極端に低下します（学校のテスト問題と答えを丸暗記したため、応用問題が解けない生徒と同じ状態です）。

    • これを防ぐため、データをあらかじめ 「学習用（7割〜8割）」 と 「テスト用（2割〜3割）」 に分割し（train_test_split）、学習にはテストデータを見せず、評価の時にだけ「実力テスト」として解かせることで、本当の予測実力を測定します。

練習問題 5: Streamlitの再実行システム（Rerun）とボタンの罠¶

Streamlitで「支払合計」を表示するアプリを作成しています。 画面に「お会計を計算する」ボタン（st.button("お会計を計算する")）を設置し、そのボタンが押された（True）ときに、客数と客単価を掛け算して「合計金額：3,500円」と画面に表示するコードを書きました。 しかし、このボタンを押して金額を表示させたあと、サイドバーに配置された「割引クーポン」のチェックボックスにチェックを入れたところ、先ほど画面に表示されていた「合計金額：3,500円」の表示が一瞬で消えてしまいました。 この現象が発生する「Streamlitの仕組み上の原因」を説明してください。

👉 練習問題 5 の解答と解説を見る

  • 正解: 「ユーザーが画面を操作するたびに、Streamlitはコードを上から下まで再実行（Rerun）し、その際にボタンのクリック状態は『False（押されていない）』に戻ってしまうから」

  • 解説:

    • Streamlitは「画面に動きがある（チェックボックスを操作するなど）たびに、Pythonコード全体を最初から完全に読み込み直す」というシステム（リアクティブ・フレームワーク）を持っています。

    • そして、st.button という部品は、**「まさにその瞬間（ボタンがカチッと押された瞬間）だけ一時的に True になり、次の再実行（Rerun）時には強制的に False に戻る」**という仕様（デザイン・パターン）を持っています。

    • そのため、ボタンが押された中のインデント処理の中に合計金額を出すコードを書いてしまうと、そのあとに別の操作（クーポンのチェックなど）をしてコードが再実行された際、ボタンの状態が False に戻り、計算処理そのものがスキップされてしまうため、表示されていた金額が消滅します。

    • 実務でこれに対処するには、ボタンの中に計算処理を書くのではなく、チェックボックスやスライダーの状態変化そのものをRerunシステムに直接検知させる（ボタンでの判定に頼らない）設計にするのが定石です。

customers_scaled_array = scaler.fit_transform(df_customers)

# (2) クラスタ数3で K-means の実行
km_model = KMeans(n_clusters=3, random_state=42, n_init=10)
labels = km_model.fit_predict(customers_scaled_array)

# (3) エルボー法のループ
distortions = []
for k in range(1, 6):
    test_model = KMeans(n_clusters=k, random_state=42, n_init=10)
    test_model.fit(customers_scaled_array)
    distortions.append(test_model.inertia_)
🎓 教員用10点満点採点・減点基準

  • 【StandardScalerによる標準化：3点】

    • StandardScaler を作成し、.fit_transform() または .fit() ➡ .transform() で2次元データを標準化できているか。生データのままK-meansに放り込んでクラスタリングしている場合は、スケール違いにより不適切な結果となるため 2点減点。

  • 【K-Means(K=3)の構築：3点】

    • KMeans(n_clusters=3, random_state=42, n_init=10) を定義し、.fit_predict() で標準化後のデータを与えてラベルを正確に取得できているか。パラメータ設定や変数指定の間違いは 1.5点減点。

  • 【エルボー法のループ実装：4点】

    • for k in range(1, 6):（あるいは 1から5 をカバーする範囲）を回し、各ループ内で定義した KMeans(n_clusters=k) に対して標準化データを .fit() させ、そのモデルの test_model.inertia_（歪みの指標）を取り出して distortions リストに .append できているか。

    • ループ範囲の間違い、テストモデルへの学習用データの渡し忘れ、test_model.inertia_ を正しくアペンドできていないなどの不備は 1点につき1点減点（最大3点減点）。
